# Verification matched to the result

Use the lowest layer that proves the changed contract. Do not run a full matrix merely
because a toolkit contains many tools. Preserve the repository's explicit required gates.

| Result             | Evidence                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| Tools installed    | Host readback with enabled plugin IDs/versions; managed CLI executable and help work             |
| Provider connected | Actual authorized context/project/schema read, not an OAuth window closing                       |
| SEO answer         | Matching saved report and coverage/time; new runs require terminal results                       |
| Sanity draft       | Exact document readback, validation and real authenticated preview                               |
| New CMS component  | CMS editing acceptance below, all query/type/render/Markdown boundaries and owning source checks |
| Published content  | Exact publication result and expected live HTML/metadata after invalidation                      |
| Code deployed      | Confirmed serving deployment; Git push and PR creation alone are not deployment                  |

For setup, separately report installed, signed in, target resolved and verified.
Use the [full setup completion gate](setup.md#completion-gate). A working preview with
pending Prime/SiteOS is incomplete; an empty installation blocker list is not evidence
of provider access. Checkpoint files record installation progress, not authenticated readiness.
Do not create live content or spend research credits solely to turn a status green.

For pages, verify the requested content and links, semantic headings/metadata, working
controls, responsive desktop/mobile layout and relevant languages. Use current locale
configuration. Check public metadata/discovery output when changed. Figma visual parity
claims require the installed Prime verification workflow and its actual evidence.

## CMS editing acceptance

For each new or materially changed CMS section, verify these applicable behaviors through
its real editor/draft preview before calling it editable and complete:

1. Change a heading or description and observe the updated rendered draft.
2. Add, reorder and delete a card/list item; confirm the rendered content and order follow
   the CMS array, and deleted content is not restored by code defaults.
3. Remove the section and verify it disappears. Empty CMS fields/arrays must not bring
   back sample content.
4. Replace media and verify the new asset, alt text and supported crop/hotspot behavior.
   Record which illustration details are fixed artwork rather than editable fields.

Use a disposable draft or isolated fixture for destructive acceptance steps. Do not delete
shared editorial content just to test removal. Mutate a real document only within the
authorized task, protect its revision and restore only the test's changes without erasing
concurrent edits. Identify the exact document, changed fields and observed preview behavior
in the evidence; never include secrets or private preview tokens.

Query/renderer tests with fixtures prove local behavior, not persisted CMS editing. Record
them separately from actual Studio operations, exact draft readback and authenticated
preview. If access, deployed schema or preview is missing, report the remaining checks as
blocked, continue safe source work and give the next step. A screenshot, schema definition,
successful build or plugin installation alone cannot pass this acceptance gate.

## Report the outcome

On failure preserve the concrete failure and completed steps. Re-read ambiguous remote
outcomes before any retry. Report unknowns honestly and request only the input/action
that unblocks the next necessary step. Keep output understandable to an editor: what
changed, where to review, whether it is live, and what remains.
