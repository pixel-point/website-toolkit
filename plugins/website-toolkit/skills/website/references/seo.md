# SiteOS evidence and improvements

Load the installed SiteOS orchestrator/shared execution contract and `siteos-seo`.
For other website reports route to the appropriate installed SiteOS skill. Do not
substitute Sanity's built-in SEO inspector for SiteOS's measured evidence.

1. Resolve authorized origin, Organization, website Project and explicit environment.
2. Use saved evidence matching the question. Report report ID/time and coverage.
   Distinguish no result, partial result and a measured zero.
3. Follow actual MCP availability. SiteOS MCP supports reads; some research/history
   reports and all new audit/research operations require the unified CLI. Use the
   installed CLI's help and the provider skill, not guessed tool names or private APIs.
4. Keep the report tied to relevant website pages, audiences and conversion intent.
   A finding is evidence to inspect, not automatic permission to rewrite product claims.
5. If the user requests a repair, trace the field to Sanity or the code, then follow
   the corresponding website workflow. Preserve excluded/illustrative findings.
6. An authorized new paid run needs its exact inputs, limits and available cost evidence;
   reuse existing authorization. No speculative reruns during setup or a saved-report read.
7. After a repair distinguish local validation, publication and a completed live recheck.
   A queued job is not a verified fix. Reconcile ambiguous writes/runs before retrying.

For a requested check of specific published URLs, follow the installed SiteOS SEO
technical-audit workflow. It supports new pages without requiring an earlier crawl.
Verify the active CLI executable, version and command help first: this capability
requires SiteOS CLI 2.34.0+ and a matching server. The toolkit's general setup minimum
does not establish support for this newer operation.

If the CLI is too old, load `siteos-cli` and update only that SiteOS installation
through its supported method, preserving any managed-tool location, working sign-in
and repository context. Respect explicit version pins and host approval requirements.
Recheck command support after updating; do not upgrade unrelated providers or run a
full toolkit `update --with-cli` merely to obtain this capability. A server capability
or access failure is a blocker, not a reason to switch identity or keep upgrading.

Keep the requested URL scope and exact environment. The URLs must be publicly
reachable on that environment's configured website origin. Do not change Production's
URL to admit a local or arbitrary preview, and never replace a blocked targeted check
with a full crawl or additional research. Wait for completion and report its actual
evidence and coverage; a local browser inspection is a separate kind of verification.

The client should receive a short page-specific action list with evidence, or the
requested completed result. Do not require Prime or a local website build merely to
read an existing SEO report. Missing GSC access does not block independent technical
evidence. Never promise ranking improvements from a successful audit or code change.
